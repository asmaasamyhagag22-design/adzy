1. إيه المشروع وإزاي بيفكّر

الفكرة: أي شركة عندها موقع → نسحب الموقع → نفهم البراند (هوية + عروض + ألوان + لوجو + جمهور) → نطلّع منه محتوى تسويقي مصمّم خصيصاً له، كل كلمة وكل لون فيه مصدره الموقع نفسه.
القيمة 1

مؤصّل (Grounded)

صفر تهيؤات. كل حقل = EvidencedField فيه (القيمة + الدليل + الثقة + نوع المصدر). الادعاءات الحقيقية لازم يكون ليها مصدر.

القيمة 2

إبداعي فعلاً

مش قوالب. الـLLM بيصمّم لكل براند تكوين مختلف من داتاه (مش "قالب مطعم" و"قالب تعليم").

القيمة 3

Universal

يشتغل لأي قطاع (مطعم/تعليم/اتصالات/مجوهرات) من غير منطق خاص بقطاع.

3. هل بيدّي البيزنس للـLLM؟ — معمارية "الحقيقتين" (Two Truth Domains)

لأ — مش بنرمي الصفحة للـLLM ونسيبه يخمّن. النظام بيفصل بين نوعين من المخرجات، كل واحد له طريقة مختلفة:
الحقيقة 1 — الحقائق (FACTS)

مؤصّلة + متحقَّق منها — مش إبداع

  • Rules أولاً (بدون LLM): استخراج deterministic للاسم (من og:site_name/title + تنظيف chrome)، CTAs، سوشيال، تواصل، بالتة، تصنيف اللوجو، العروض المعروفة.
  • LLM للحقول الصعبة (~4 نداءات gpt-4o-mini): العروض، الـpositioning/value-props، trust signals. الـLLM بياخد جزء مُحزَّم من نص الموقع (مش الموقع كله).
  • Validator (zero-hallucination): كل حقل/عنصر طلع من الـLLM بيتقارن بالأدلّة — أي عنصر مش مدعوم بيتشال (مثال Orange: اتشال عرض واحد غير مدعوم؛ rejections=1).

النتيجة: الـLLM أداة استخراج مش مصدر الحقيقة. لو الكلمة مش في الموقع، بتترفض.

الحقيقة 2 — التصميم/الكوبي (DESIGN)

إبداع حر — لكن مربوط بالهوية

  • الـLLM بيصمّم: تكوين البوستر (layout/scene)، فكرة الـImagen، الكوبي الإعلاني، الـstoryboard.
  • بس بيتغذّى بالـpersona الحرفية (تاجلاين/وصف/قيم/جمهور/لغة/بالتة) فالتصميم يخصّ هذا البراند.
  • أي ادعاء حقيقي في الكوبي لازم مصدره من بحث حقيقي (مثال: angle بيدّعي رقم/جائزة لازم URL رجع من البحث فعلاً — وإلا بيتنزّل لـ'profile').

يعني: التصميم مايتجمّدش بقاعدة الـzero-hallucination، لكن الحقائق فيه بتتحقّق.

خلاصة للمناقشة: المعمارية Hybrid: Rules + LLM-then-Validated للحقائق، وLLM-creative للتصميم. الموديلات الافتراضية: استخراج البروفايل = gpt-4o-mini؛ شغل البوستر/الريل الإبداعي = Gemini 2.5 (Vertex) (يستهلك كريديت GCP مش مفتاح OpenAI) مع OpenAI fallback؛ الصور = Imagen 4 Ultra؛ الفيديو = Veo (Vertex) أو KenBurns على الصور الحقيقية؛ الـvoiceover = Gemini TTS.

4. إزاي أفرّق بين موقعين تعليميين — كل واحد له شخصيته

السر: الشخصية بتيجي من الداتا، مش من قالب القطاع. النظام بيمنع نفسه عمداً من أي "قالب تعليم" (قاعدة universal) — الفرق بيطلع من بصمة كل براند.

بصمة كل براند (الـprofile):

تاجلاين + وصف + value propositions حرفية  •  البالتة الحقيقية  •  اللوجو الحقيقي  •  العروض الحقيقية  •  الجمهور/النبرة/اللغة  •  الدولة (من الـccTLD)  •  الصور الحقيقية للمكان.

الـcreative engine بياخد البصمة دي ويبني concept يجسّدها:

المُدخل المختلفالمُخرج المختلف
تاجلاين/وصف مختلفهيدلاين وفكرة مشهد مختلفة

6. المشاكل اللي واجهتنا وحلّناها

اللوجو

لوجو مكسور/غلط

inline-SVG (Vodafone) → نـrasterize اللوجو الحقيقي عبر المتصفح مع visibility gate (مايطلّعش لوجو فاضي).

بانر-كلوجو + أيقونة إيميل كلوجو → حُرّاس بالـconfidence/الكلاس + عقوبة روابط التواصل.

لوجو أبيض → بلاطة غامقة luminance-aware. النتيجة: 46% → 83%+ لوجو صح.

البوستر

خلفية off-brand

راجل غربي + نص مخبوز → السبب كان موديل Imagen الأخف؛ الحل: Ultra + region anchor (ccTLD) + برومبت مؤصّل يقود بالـsubject/الدولة/البالتة.

accent غلط → أكثر لون مشبّع legible من البالتة الحقيقية.

الريل

كان بيكراش وشكله وحش

موديل Veo 404 → الموديل الصح + per-scene fallback (مايكراش أبداً).

كتابة وحشة → إعادة تصميم: بلوك سفلي + scrim قوي + typography هرمية + accent highlight + CTA chip.

voiceover → Gemini TTS على كريديت GCP.

السكرابر

مواقع قوية/مهيكلة

redirects للساب-دومين → مطابقة eTLD+1 (Vodafone: 40 رابط رجعوا internal).

مواقع مبلوكة → deep-search fallback من نتائج البحث.

صور CSS-background/lazy → جمع الصور الحقيقية للمكان (elkbabgi 0→20).

الاسم

chrome في الاسم

"Website"/"E-Shop" → تنظيف whole-word عند المصدر (Vodafone Egypt E-Shop → Vodafone Egypt).

التأصيل

تسريب ادعاء غير مصدّق

URL مفبرك من الموديل كان بيعدّي كـcitation → المصدر لازم يكون من نتائج البحث الحقيقية، وإلا "profile" (مراجعة عدائية لقت + صلّحت 7 باجات).

7. المشاكل اللي لسه عندنا (Backlog)

palette-extraction بيفوّت لون البراند الأساسي أحياناً (Orange #ff7900 مش اتلقط → الـaccent طلع أزرق). مهم

بعض المواقع 0 لوجو candidates / 0 صور محتوى → wordmark / ريل gradient. (76% من البروفايلات القديمة ملهاش صور — محتاجة re-scrape).

AIML Veo 3.1 مبلوك بـCloudflare (الـUser-Agent الافتراضي) — الحل: browser UA (لسه). دلوقتي بنستخدم KenBurns/Veo-3.0.

عنوان الريل = التاجلاين الحرفي إلا لو شغّلتيه بـ--from-plan/research.

stealth للمواقع المحميّة بقوة (Akamai/DataDome) — محتاج deep-search مش تجاوز WAF.

page-type misclassification أحياناً (terms/privacy → services) + SSRF depth (sub-pages/redirects).

8. الأوامر — من السكراب للريل

# 1) سحب الموقع → manifest
python -m scraper "https://www.orange.eg/en/"

# 2) manifest → profile  (لوجو + اسم نضيف تلقائياً)
python -m business_profile scrapes/<slug>/manifest.json -o profile.json

# 3) بوستر  (Imagen Ultra + كوبي مؤصّل + يركب ترند)
python -m poster profile.json --out poster.png --trend

# 4) تقويم محتوى راكب على الترندات
python -m strategy profile.json --days 30 --trends --out plan.json

# 5) ريل  (KenBurns على الصور الحقيقية = يتخطّى AIML + Gemini voiceover)
python -m reel profile.json --out reel.mp4 --real

# 6) (اختياري) فنّي التقويم كله لبوسترات + ريلز
python -m campaign profile.json --from-plan plan.json

ملاحظة: متفرضيش IMAGEN_MODEL=imagen-4.0 (سيبيه Ultra). لإيقاف AIML نهائياً: REEL_VIDEO_BACKEND=vertex في .env.

9. النقلة الجاية: Agent Frameworks (LangGraph / CrewAI / MCP / Crawl4AI)

الوضع الحالي: pipeline يدوي deterministic + LLM callers محقونة (protocols + providers قابلة للتبديل). ده أساس ممتاز للنقلة لأنه modular بالفعل.

المبدأ الذهبي وإحنا بننقل (مهم جداً للمناقشة):

الـmoat (التأصيل) لازم يفضل جوّه الأدوات (Tools)، مش في حكم الـAgent.
الـAgent بيـينسّق (orchestrate)؛ الأدوات الـdeterministic + الـValidator هي اللي بتفرض الحقائق. ماينفعش نسيب الـagent "يألّف" حقائق — وإلا نخسر الميزة الأساسية.
خطوة 1 — الأسهل/الأقوى

MCP Servers

نغلّف كل قدرة كأداة MCP: scrape_url · build_profile · generate_poster · generate_reel · discover_competitors · build_strategy. كده أي MCP client (Desktop apps, IDEs) يقدر يستدعي المشروع كـtoolbox. أقل مخاطرة، أعلى رافعة.

خطوة 2 — التنسيق

LangGraph

نمثّل التدفّق التكيّفي كـgraph بحواف شرطية: مبلوك → deep-search؛ 0 منافسين → standalone SWOT؛ ecommerce → web-discovery. بيدّي retries + state + observability. (LangChain للـchains البسيطة، LangGraph للحالة والتفرّع.)

خطوة 3 — أدوار

CrewAI (multi-agent)

وكلاء بأدوار: Researcher / Strategist / Designer / Critic بيستخدموا أدوات الـMCP. الـCritic يفرض التأصيل (فحص عدائي — زي workflow المراجعة اللي شغّلناه فعلاً ولقى 7 باجات).

السكرابر

Crawl4AI

بديل/مكمّل للـPlaywright scraper — crawler صديق للـLLM (markdown نضيف + استخراج مهيكل). نقدر نخليه أداة الـscrape البديلة، خصوصاً للمواقع الصعبة.

الاتجاه الأكبر

من أداة → منتج SaaS

محرك الترندات + تقويم المحتوى + الـcampaign dispatcher (اتبنوا فعلاً) = نواة المنتج. + لوحة observability للتوكن/التكلفة لكل node (الـUsage موجود). + جدولة ونشر.

مسار النقل العملي باختصار (للتنفيذ)
  1. غلّف كل module كـMCP tool (input/output schemas واضحة — موجودة كـPydantic بالفعل).
  2. اكتب LangGraph orchestrator فوق الأدوات دي، بنفس الحواف الشرطية الموجودة في الكود (router/full_run).
  3. أضف Critic agent يكرّر فحص التأصيل قبل التسليم (نمط الـadversarial verify).
  4. سيب الـValidator + الـextractors deterministic جوّه الأدوات — الـagent مايلمسش الحقائق.
  5. observability: اجمع الـUsage لكل node في لوحة (توكن/تكلفة/زمن).
